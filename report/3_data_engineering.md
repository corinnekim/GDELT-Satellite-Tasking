# 3. 데이터 전처리

## 3.1 전처리 목표

GDELT 원본(2026년 32일치, 약 271만 행, 약 2.1 GB)을 개인용 노트북 메모리에 무리 없이 들어가는 정제 parquet으로 변환해, 이후 칼만 필터·LLM 검증·위성 스케줄링이 모두 같은 입력 파일을 빠르게 읽도록 만드는 것이 목표이다.

## 3.2 핵심 처리

전처리는 DuckDB SQL을 핵심 엔진으로 사용한다. Pandas로 처리하려면 271만 행을 한 번에 메모리에 올려야 하지만, DuckDB는 필요한 컬럼과 행만 디스크에서 읽어 곧바로 가공해 결과를 디스크로 보내므로 메모리 사용량이 입력 크기와 거의 무관하다. 필터링, 타입 변환, 문자열 가공, parquet 저장을 모두 단일 SQL 쿼리에 묶어 중간 DataFrame이 생기지 않게 했다.

### (1) 데이터 타입 최적화

GDELT 원본은 거의 모든 정수 컬럼을 INT64로, 실수를 DOUBLE로 저장하지만 실제 값 범위에 비해 과도한 타입이다. 값 범위에 맞는 가장 작은 타입으로 변경해 행당 메모리를 약 50~60% 줄였다 (표 1).

**표 1. 주요 컬럼의 타입 최적화 결과**

| 컬럼 | 원본 → 변환 |
|---|---|
| GLOBALEVENTID | INT64 → UINT32 |
| SQLDATE | INT64 → INT32 |
| IsRootEvent, QuadClass, ActionGeo_Type | INT64 → TINYINT |
| EventCode, EventRootCode | INT64 → INT16/INT8 |
| GoldsteinScale, AvgTone, 위경도 | DOUBLE → FLOAT |
| NumArticles, NumSources | INT64 → INT16 |

### (2) 도시명만 남기기

`ActionGeo_FullName`은 "Tehran, Tehran, Iran" 같은 형태로 되어 있다. 후속 분석은 도시 단위로 이루어지고 행정구역·국가는 다른 컬럼에 별도로 들어 있으므로, 첫 번째 콤마까지만 잘라내 "Tehran"만 남긴다. 평균 25~30자였던 문자열이 7~10자로 줄어든다.

## 3.3 결과

원본 2,118 MB가 정제 후 1,212 MB로 약 57% 줄었다. 정제 결과물은 칼만 단계가 사용하는 메인 데이터(399 MB)와 LLM 검증 단계에서만 로드되는 URL 데이터(812 MB)로 분리되어 있어, 칼만 단계의 메모리 사용량은 399 MB에 그친다. 이후 칼만 필터, LLM 검증, 위성 스케줄링은 이 두 묶음을 메모리 압박 없이 읽어 동작한다.
